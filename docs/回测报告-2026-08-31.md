> 回测对象：`http://127.0.0.1:5270/`（本机绿色版 v1.1，数据库 `data/hr.db`）
> 回测依据：`使用说明.md`（v1.1 一期完整版）＋ `docs/人事AI工作台-设计方案-v2.0-本机绿色版.md`
> 回测日期：2026-08-31
> 回测方式：页面/API 全量冒烟 ＋ 业务规则落库校验 ＋ 解析引擎专项 ＋ 边界健壮性 ＋ 并发性能

## 一、总体结论

系统**骨架完整、跑得通、性能很好**（12 个页面全 200，首屏 15~26ms，10 并发读写 0 错误）。但存在 **5 个 P0 级缺陷**，其中 3 个直接击穿产品核心承诺（到期提醒）、1 个是敏感数据明文泄漏、1 个是法条表述写反的合规风险。

| 级别 | 数量 | 性质 |
|---|---|---|
| **P0 严重** | 5 | 核心功能失效 / 敏感数据泄漏 / 合规错误，必修 |
| **P1 重要** | 9 | 功能正确性、健壮性、访问控制 |
| **P2 一般** | 8 | 架构承诺、文档一致性、可维护性 |

**最需要优先处理的三件事**：① 合同变更后不触发提醒扫描（核心卖点失效）② 员工详情页身份证/银行卡明文泄漏 ③ 法条表述写反。

## 二、P0 严重缺陷（必修）

### P0-1 新增/修改/导入合同后，待办中心不会生成提醒

**依据**：使用说明「合同台账与到期提醒」—"系统自动提醒……所有提醒汇总到待办中心"。

**实测**：新增 4 个应触发提醒的合同（30 天到期、第 2 次合同、试用期 10 天到期、已过期 5 天）→ `todo_item` 表 **0 条**。手动调用 `sync_contract_todos()` 后才出现 3 条。

**根因**：`app/services/reminders.py` 的 `sync_contract_todos()` 只在两处被调用：

- `app/main.py` 的 `@app.on_event("startup")` —— 仅启动一次
- `app/abilities/scheduler.py` —— `cron 9:00` + `interval 6h`

而 `api.py` 的 `contract_add` / `contract_update` / `contract_delete` / `contract_import` **四个入口都没有调用它**。用户上午录入一份明天到期的合同，待办中心在当天 9 点前或下个 6 小时周期前都是空的。

**修复建议**：在合同 add/update/import/delete 提交后同步调用 `sync_contract_todos()`（单机量小，毫秒级，无需异步）。

---

### P0-2 员工详情页：身份证 / 银行卡明文泄漏在 HTML 源码中

**依据**：使用说明「员工档案」—"身份证/银行卡**默认掩码**显示"；设计文档 3.4 —"敏感字段……**字段级加密存储**，UI 默认掩码显示"。

**实测**：`/employees/1` 返回的 HTML 中，`110101199005201234`、`6222020200012345678` **完整明文存在**。

**根因**：`web/templates/employee_detail.html` 两处渲染方式不一致：

```html
<!-- 第 37-38 行：编辑表单，明文输出（虽 display:none 但源码可见） -->
<input name="id_card" value="{{ e.id_card }}">
<input name="bank_card" value="{{ e.bank_card }}">

<!-- 第 53-54 行：档案信息区，才走掩码 -->
<tr><td>身份证</td><td>{{ mask(e.id_card) or '-' }}</td></tr>
```

下方区块标着"敏感字段默认掩码"，上方表单却把明文原样吐给浏览器。**查看源代码、浏览器自动填充、密码管理器、截图分享都会泄漏**。

**附带**：数据库里也是明文存储（`models.py` 注释自认"敏感字段明文存储但 UI 默认掩码"），未达到设计文档要求的字段级加密。

**修复建议**：① 表单 `value` 一律走 `mask()`，需要真正编辑时再做"点击显示明文"的二次交互；② 或改为编辑页不回填敏感字段（留空＝不修改）；③ 中长期按设计文档做加密存储。

### P0-3 面试到期提醒完全未实现

**依据**：使用说明「面试安排与跟进」—"到期提醒进入待办中心（无邮件提醒，一期仅界面提醒）"。

**实测**：新增一条明天的面试 → 待办中心无该条目。全库 `grep` 确认：**没有任何代码生成 `kind='interview'` 的待办**，`TodoItem` 的写入点只有手动新增和合同扫描两处。

**根因**：`sync_contract_todos()` 只扫 `Contract` 表（函数 docstring 写的是"扫描合同/面试"，但函数体里没有面试逻辑）；`scheduler.py` 也只注册了这一个函数。

**修复建议**：新增 `sync_interview_todos()`，扫描 `status in ('待确认','已预约')` 且 `start_time` 在未来 1 天/当天/已逾期的面试，并在 `interview_add/update/status` 与 scheduler 中触发。

### P0-4 劳动合同法第 14 条表述写反（合规风险）

**位置**：`app/services/reminders.py:59`

```python
f"...按劳动合同法第14条，劳动者提出时第3次应订立无固定期限合同"
```

**法条原意**（《劳动合同法》第 14 条第 2 款第 3 项）：连续订立二次固定期限劳动合同，且劳动者无法定例外情形，续订劳动合同时，**除劳动者提出订立固定期限劳动合同外，应当订立无固定期限劳动合同**。

**问题**：代码写的是"**劳动者提出时**应订立无固定期限"，与法条**完全相反**。正确逻辑是"**劳动者不提出固定期限时**，默认应订立无固定期限"。

这是 HR 会直接引用答复员工、甚至影响续签决策的文案，表述反了可能引发劳动争议。

**修复建议**：改为"按劳动合同法第 14 条，本次续订时**除劳动者本人提出订立固定期限外**，应当订立无固定期限劳动合同。另有第 39 条、第 40 条第 1/2 项情形的除外。附：本提示不构成法律意见。"

### P0-5 每日自动备份完全未实现

**依据**：使用说明「数据与备份」—"自动备份：每日首次启动自动备份 hr.db 到 `data/backups/`，保留最近 7 份"。

**实测**：`data/backups/` **空目录**。全库 `grep backup` 只命中 `config.py`（读取配置项）和 `database.py`（建目录），**没有任何执行备份的代码**。

**根因**：`Config` 读了 `backup_on_start` / `backup_keep`，但 `main.py` 的 startup 流程里没有调用备份逻辑。配置项是"空头支票"。

**修复建议**：`main.py` 启动时按日期标记做单次备份 + 滚动删除超过 `backup_keep` 的旧文件。

## 三、P1 重要缺陷

### P1-1 简历解析：姓名抽取失败（最基础字段）

`app/abilities/resume_parser.py:150`

```python
name_m = re.search(r"(?:姓名|名字)[：:\s]*(.{2,8})", text)
```

**强制要求"姓名："标签**。而真实简历（尤其平台导出）姓名通常在首行且**无标签**。

实测：简历首行是"张三"→ `name=''`（空）。姓名是最核心字段，缺失会导致候选人列表全空、去重失效。

**建议**：增加回退策略 —— ① 首行短文本（2~4 汉字且非板块标题）② 文件名去扩展名 ③ 提高置信度区分。

---

### P1-2 简历解析：技能子串误判（直接影响初筛结果）

`resume_parser.py:242`

```python
skills = [s for s in SKILLS if s in text_lower]   # 裸子串包含
```

实测误判：

| 简历原文 | 实际命中 | 误判项 |
|---|---|---|
| 熟悉 **MongoDB** | go, mongodb | "go" 命中 Mongo**go**db |
| 精通 **Django** | go, django | 同上 |
| 会用 **JavaScript** | java, javascript | "java" 命中 Java**Script** |
| MySQL | mysql, **sql** | "sql" 命中 My**SQL** |

技能是**硬条件过滤项**（`_check_hard`），误命中会让不满足技能要求的候选人直接通过硬过滤，污染三档结果。

**建议**：改为词边界匹配（`\b` 不适用于中文，需按分隔符切词后精确比对），并移除 `go`/`sql`/`c` 等易冲突短词或加前后界定。

---

### P1-3 简历解析：工作年限计算错误

`resume_parser.py:22` `EXPERIENCE_RE = r"(\d+)[+\-]?\s*年(?:以上)?(?:工作)?经验"` —— 要求必须出现"经验"二字。

实测：简历写"工作年限：5年"（无"经验"）→ 正则漏配 → 回退到日期区间推算 → `DATE_RANGE_RE` 又只匹配到 1 段（"2023-至今" 未匹配上）→ 得出 **3.0 年**（正确应约 5~6 年）。

**建议**：① `EXPERIENCE_RE` 增加"工作年限/年限"变体；② 排查 `DATE_RANGE_RE` 对"2023-至今"的匹配；③ 年限是硬条件，错误会直接误判档位。

---

### P1-4 简历解析：工作经历段数识别错误

同一份简历明明 2 段经历（2020-2023 A公司、2023-至今 B公司），`job_changes` 识别为 **1**。该值用于稳定性评分（`_score_soft` 中 ≤2 段加分），失真会直接影响软评分。

根因同 P1-3 的 `DATE_RANGE_RE` 漏匹配。

---

### P1-5 置信度标注虚高，误导人工复核

使用说明承诺"详情页黄色字段为低置信度，直接改后保存"—— 意味着用户**会信任未标黄的字段**。

实测：`work_years` 值完全错误（3 年 vs 实际 5 年）却标 `0.9`；`skills` 含误判项也标 `0.9`。

**问题**：置信度是硬编码常量（`put(..., 0.9)`），不反映实际抽取过程的不确定性。用户会跳过复核，错误数据直接流入初筛决策。

**建议**：置信度按抽取路径动态赋值（正则精确命中 0.9 / 回退推算 0.5 / 未命中 0.0）。

---

### P1-6 批量简历上传：单个坏文件导致整批回滚

实测：同时上传 `good1.txt`（合法）+ `bad.doc`（不支持格式）→ HTTP 400，**good1.txt 也未入库**（1 条 → 1 条，无新增）。

**根因**：`resume_upload` 循环中 `_save_and_parse()` 无 try/except，`extract_text` 对不支持格式直接 `raise HTTPException(400)`，整个事务回滚。

另注：`RESUME_EXTS` 包含 `.doc`，但 `extract_text` 明确不支持 `.doc`（只支持 txt/md/docx/pdf）—— 代码自我矛盾，用户按扩展名列表上传 `.doc` 必失败。

**建议**：① 单文件异常 catch 后计入"跳过"计数，不中断批次；② 从 `RESUME_EXTS` 移除 `.doc` 或实现转换；③ 返回页展示"成功 N / 跳过 M"。

---

### P1-7 FTS5 索引建了不用，且删除只留墓碑

`app/routers/api.py:344` 检索实现：

```python
where = " AND ".join(f"kc.content LIKE :p{i}" ...)   # 实际走 LIKE 全表扫描
```

代码注释称"trigram 分词器会为 LIKE 自动走 FTS 索引"——**这是错误认知**。FTS5 不会加速普通表的 LIKE 查询，`LIKE '%x%'` 必然全表扫描。

实测证据：`chunk_fts` 表被 `init_fts()` 创建、`_fts_insert/_fts_delete` 维护，**但从未被任何 SELECT 查询**；删除文档后 FTS 的 `chunk_fts_data` 行数**从 13 增到 14**（FTS5 的 delete 是写墓碑，不是真删）。

**影响**：纯负债 —— 每次上传/删除都额外写索引却不产生任何收益，且墓碑无限增长。

**建议**：二选一 —— ① 检索改用 `chunk_fts MATCH`（2 字中文词需改 jieba 分词或 LIKE 兜底并存）；② 直接移除 FTS 相关代码，保留 LIKE（当前数据量下 <50ms 完全够用）。

---

### P1-8 常用回复快捷编号可重复

使用说明承诺"搜索（支持 /nj 快捷编号）"。实测新增一条 `shortcut='/nj'` 成功，库中 `/nj` 变成 2 条 —— 搜索时结果歧义，用户无法预期命中哪条。

**建议**：`reply_add` / `reply_update` 校验 `shortcut` 唯一性（空值不校验），冲突时返回明确提示。

---

### P1-9 全系统零认证、零访问控制

实测：全库 `grep -iE "login|auth|password|session|current_user|token"` 在业务代码中**零命中**，`/salary`（工资明细）、`/employees`（身份证/银行卡）等敏感页面均可无鉴权直接访问。

**风险**：设计文档 3.5 明确要求"如需局域网/手机访问，配置文件里改 `host: 0.0.0.0` **并设置访问口令**"；第 8 章要求"可选启动口令"。但 `配置.yaml` 里 `host` 是一个**裸露的可改项**，没有任何配套口令机制。

用户按配置注释改成 `0.0.0.0` 后，含身份证、银行卡、全员薪资的 HR 库会在局域网内完全裸奔。

**建议**：① 检测 `host != 127.0.0.1` 时强制要求配置 `access_password` 并拒绝启动（或在页面顶部显著告警）；② 至少实现单口令登录。

## 四、P2 一般问题

### P2-1 "绿色免安装"名不副实

设计文档 3.5 方案 A 要求内嵌 portable Python（`runtime/python/` + `runtime/site-packages/`），"拷贝目录 = 安装"。

实测：**`runtime/` 目录不存在**，`启动工作台.bat` 回退 `set PY=python`。当前进程跑在**系统 Python 3.14** 上（`C:\Users\Amy\AppData\Local\Programs\Python\Python314\python.exe`）。

拷到一台没装 Python（或没装依赖包）的电脑，双击即失败。核心卖点失效。

**建议**：补 `build/build.bat` 生成 `runtime/`；`.bat` 在 `runtime` 缺失时给出明确中文提示而非静默回退。

---

### P2-2 年假未按条例第五条做折算

`web/templates/leave.html:53` 只返回全年额度（5/10/15 天）。但《职工带薪年休假条例》第五条规定，年中入职/离职应按**当年度剩余日历天数折算**（`当年已过日历天数/365 × 全年应享天数`，不足 1 天不计）。

当前实现下，一个 12 月入职的员工也会显示"年假 5 天"。

---

### P2-3 假期计算纯前端，无留痕、不可导出

计算逻辑全部在 `leave.html` 的内联 JS 中，无后端校验、无审计日志、结果不可导出/归档。HR 给员工的年假答复无法追溯。
